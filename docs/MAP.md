# MAP

burrow is an ssh client and server in wolf. This map says what it is made
of, what it speaks and refuses, and what is measured where. Sources are in
[SOURCES](SOURCES.md).

`burrow` logs in with an Ed25519 key, runs one command on a session channel
with stdin, stdout and stderr as raw bytes, and exits with the command's
status (255 for every refusal), taking the command line den passes. With
no command it starts the login shell with no pseudo-terminal (under `-T`,
or when stdin is not a terminal), as `ssh -T` does, so `ssh -T
git@github.com` shows GitHub's greeting and exits with GitHub's status; at a
terminal without `-T` it refuses by name before connecting
(`pty_unsupported`). Linked as `ssh` on PATH, it carries den's
clone, fetch and push byte for byte as the pinned `ssh` does
(`tools/check-den`).

## What burrowd speaks

The same profile from the server's side. Its KEXINIT is the client's with
the server's indicators: kex `curve25519-sha256`,
`curve25519-sha256@libssh.org`, `ext-info-s`,
`kex-strict-s-v00@openssh.com`; the same host key, cipher, MAC and
compression lists. Negotiation takes the client's lists first (RFC 4253
§7.1). EXT_INFO follows the first NEWKEYS when the client offered
`ext-info-c`, with `server-sig-algs` `ssh-ed25519` alone. Its identification
is `SSH-2.0-burrowd_0.0.0`. A session channel is confirmed with window 0
and maximum packet 32768, as the pinned `sshd` confirms it, and the window
opens when the command starts.

## What burrowd refuses, by name

Each refusal is one log line's `outcome` (or, for one that does not end the
connection, a name in its `refused` list). Where the pinned `sshd` sends a
DISCONNECT for the same condition, burrowd sends the same reason code and
text, so the pinned `ssh` prints the same bytes, and the name is in the log
alone; elsewhere the text is `burrowd: <name>: <detail>`.

**At start**, exit 1 and nothing listens: `host_key_missing`,
`host_key_permissions` (a group- or world-accessible key, or one owned by
another user than root or the running user), `host_key_unreadable`,
`host_key_malformed`, `host_key_unsupported`, `host_key_encrypted`,
`config_unknown` (a keyword `sshd_config(5)` does not list),
`config_unsupported` (one it lists that burrowd lacks, or a value burrowd
does not take), `option_unknown`, `option_unsupported`, `usage`,
`listen_failed`, `privileges_unsupported` (root where the user cannot be
changed: macOS) and `preauth_user_missing` (root without the `burrowd`
account); `config_unsupported` too for `PasswordAuthentication yes` when
burrowd is not root (px112: only root reads `/etc/shadow`).

**Per connection:**

| name | when | the pinned `ssh` prints |
|---|---|---|
| `startups_exceeded` | MaxStartups drops the connection before any byte | `kex_exchange_identification: read: Connection reset by peer` |
| `grace_expired` | not authenticated within LoginGraceTime | the connection closes, as `sshd`'s does |
| `strict_kex_missing` | no `kex-strict-c-v00@openssh.com` in the client's first KEXINIT | (a scripted client: DISCONNECT 3) |
| `no_common_kex`, `no_common_hostkey`, `no_common_cipher` | negotiation | the client finds it first: `Unable to negotiate with … Their offer: …`, byte for byte as against `sshd` |
| the transport's names (`packet_too_long`, `message_unexpected`, `mac_mismatch` and the rest above) | the shared transport, against a scripted client | DISCONNECT with the client's codes |
| `service_refused` | a service other than `ssh-userauth` | |
| `auth_method_refused` | `none`, `keyboard-interactive`, `hostbased`, and `password` while `PasswordAuthentication` is `no` (named, not final) | `Permission denied (publickey).` once `ssh` has spent its methods |
| `auth_account_locked`, `auth_account_expired` | (px112, every method, `sshd(8)`'s rule) the account's `/etc/shadow` password starts with `!`; its expiry date, or its password's inactive period, has passed | `user@127.0.0.1: Permission denied (publickey,password).` |
| `auth_password_bad`, `auth_password_unset`, `auth_password_empty`, `auth_password_unsupported`, `auth_password_over_cap`, `auth_password_expired`, `auth_password_too_long`, `auth_password_change_refused` | (px112, `PasswordAuthentication yes`) the wrong password; no password (`*`, no line); an empty field (`PermitEmptyPasswords no`); a crypt(5) method other than `$7$`; a `$7$` string over the shipped cost; field 3 `0` or the maximum age past (a key still logs in); over 1024 bytes; RFC 4252 §8's change request. Each after the same one hash, but the last two, which run none | `Permission denied, please try again.`, then `user@127.0.0.1: Permission denied (publickey,password).` |
| `auth_key_unlisted`, `auth_user_unknown`, `auth_root_refused`, `auth_strict_modes`, `auth_key_unsupported` | no line admits the key; no such account; root, always; StrictModes; a key that is not `ssh-ed25519`. Alike to the client, so no account is disclosed | `user@127.0.0.1: Permission denied (publickey).` |
| `auth_sig_bad` | a signature that does not verify over the monitor's own session identifier: another session's, another key's | (a scripted client: USERAUTH_FAILURE) |
| `auth_tries_exceeded` | MaxAuthTries | `Received disconnect from … :2: Too many authentication failures` |
| `auth_changed` | the user or service changed between requests | (a scripted client: DISCONNECT 2) |
| `channel_type_refused`, `session_limit` | a channel other than one session | `-W`: `channel 0: open failed: administratively prohibited: open failed` |
| `forward_refused`, `request_refused` | `tcpip-forward` and the like; any other global request | `-R`: `Error: remote port forwarding failed for listen port 0` |
| `pty_refused`, `shell_refused`, `subsystem_refused`, `x11_refused`, `agent_refused`, `signal_refused`, `env_refused`, `exec_twice`, `request_refused` | each channel request burrowd does not take (named, not final; the command still runs where `sshd` runs it) | `PTY allocation request failed on channel 0`, `shell request failed on channel 0`, `subsystem request failed on channel 0`, as against `sshd` |
| `channel_unknown`, `channel_closed`, `window_exceeded`, `channel_packet_too_large`, `window_overflow` | the client's channel misbehaves | (a scripted client: DISCONNECT 2) |
| `nologin`, `exec_failed` | `/etc/nologin` exists (its text on stderr); the shell cannot start | |
| `disconnected`, `closed`, `timeout`, `io` | the client's DISCONNECT, the socket's end, a deadline, a failure | |

A session that ran ends with outcome `ok` and its exit status or signal.

Where the pinned `ssh` prints a line for the same failure, burrow prints that
line first, with the program's own name where `ssh` prints its own
(`ssh: connect to host … port …: Connection refused` when burrow runs as
`ssh`), then `burrow: <name>: <detail>`. A server-opened channel (`x11`,
`auth-agent@openssh.com`, any type) is answered OPEN_FAILURE reason 1 and
named `channel_open_refused` in a debug line; the session goes on.

`burrow-keygen` refuses by name too, exiting 1 as `ssh-keygen` does:
`exists` (it never overwrites), `type_unsupported`, `passphrase_unsupported`,
and the `key_*` names for `-y` and `-l`.

## burrowd's processes

Where burrowd runs as root (Linux; PAX in B6), no byte from the network is
parsed as root, and the host key's private half is held only by the
process that signs with it:

| process | runs as | holds | does |
|---|---|---|---|
| listener | root | no private key (a forked child checks the key at start and exits) | accepts, counts unauthenticated connections from a pipe per monitor (MaxStartups), reaps |
| monitor, one per connection | root | the host key, read after its two children are forked; the session identifier; `/etc/shadow`'s text (px112) | signs exchange hashes; reads passwd, group, shadow and `authorized_keys`; checks the account's lock, StrictModes, the key and the signature; counts tries; writes the log line |
| worker | the `burrowd` account, cwd `/` | the connection, before authentication | the version, KEXINIT, ECDH, the service and USERAUTH requests, asking the monitor over bounded frames; then hands the transport's state to the monitor and exits |
| holder, then the session | root holding nothing, then the user's uid, gid and groups with no way back | the transport's state, after authentication | the session channel; asks the monitor to sign at a re-exchange |
| the command | the user | its three pipes | the user's shell with `-c` |
| checker, one password (px112) | root, forked by the monitor, one at a time across the server (a one-byte token the listener keeps in a pipe, put back by the listener when a monitor ends holding it) | the monitor's memory, the password and the field | scrypt at the field's cost (at most N = 2^17, r = 8, p = 1: 128 MiB), exits 0 on a match; the memory leaves with it |

The session can ask the monitor to sign an exchange hash for as long as it
lives, as any server whose post-authentication process re-keys without the
host key must allow. Without root (any host), and on macOS always, the same
processes run as the invoking user, and serve only that user.

## Constant time

The one comparison of secret-dependent data burrow makes itself is the
Poly1305 tag check in `chachapoly.open`, through `wire.ct_eq`: every byte
pair is folded into one accumulator before anything is tested, and nothing
is decrypted before it passes. Key derivation, the exchange hash, X25519,
ChaCha20 and Poly1305 are wolf-std's and carry its `ct:` lines. Host keys,
signatures and the exchange hash the server signs are public.

**The user key's signature is not constant time.** burrow signs once per
login with wolf-std's `curve25519.sign`, whose scalar multiplication adds
under a branch on each bit of the secret scalar (std's own `ct:` line
records it as an obligation for its constant-time tier). The seed is never
branched on or indexed by in burrow's own code (`src/keyfile`, `src/auth`).
The hashed known_hosts comparison and the key file's check words use
`wire.ct_eq`, though neither guards a secret.

**burrowd's host key signature is not constant time either,** for the same
reason: the monitor signs each exchange hash with `curve25519.sign`. The
signatures it verifies, and the keys it compares, are public.

| MAC | the five `-etm` variants, then `umac-64@openssh.com, umac-128@openssh.com, hmac-sha2-256, hmac-sha2-512, hmac-sha1` |
| compression | `none, zlib@openssh.com` |
| EXT_INFO | `server-sig-algs`, `publickey-hostbound@openssh.com`, `ping@openssh.com` |

B2 and B3's black-box findings (`tools/check-session` holds each):

- The pinned `ssh` sends `none` first, queries with plain `publickey`, then
  signs with `publickey-hostbound-v00@openssh.com`; burrow sends no `none`
  (unless it has no identity) and signs with plain `publickey`.
- Its log lines end in CR LF; burrow's in LF. Rows compare lines.
- It shows a banner with every byte outside TAB, LF, CR and printable ASCII
  as `\ooo` (C locale), adding no newline.
- OpenSSH 10's per-source penalties refuse 127.0.0.1 after a few failed
  logins; the rows' `sshd` turns them off.
- `-l` wins over `user@host`.
- A remote killed by a signal: exit 255, nothing printed.
- The session channel is confirmed with window 0 and maximum packet 32768,
  and the window opens once the command runs.
- Under `StrictHostKeyChecking=no` a changed key is warned of and the login
  goes on (password methods disabled), and nothing is written; an unknown
  host's line is `name ssh-ed25519 base64`, hashed as HMAC-SHA1 keyed by the
  20-byte salt under `HashKnownHosts`, and `HostKeyAlias` names it.
- `ssh-keygen` writes 0600 and 0644, base64 in 70-column lines, pads the
  private section to 8 with 1, 2, 3…, prints `-y` with the comment, and on an
  existing file asks to overwrite and exits 1 with no answer.

Three black-box findings shape B1:

- **Sealed frames align `packet_length`, not the whole frame.** Under
  `chacha20-poly1305@openssh.com` the pinned `sshd`'s first sealed packet has
  `packet_length` a multiple of 8, and RFC 4253 §6's whole-frame rule refused
  it (`unaligned`). burrow sends and expects the measured rule; plaintext
  frames keep §6's.
- **No re-exchange before user authentication.** The pinned `sshd` logs a
  client KEXINIT after SERVICE_ACCEPT as a protocol error and answers it with
  UNIMPLEMENTED; it does not start one itself there either. burrow refuses by
  name (`kex_failed`) rather than wait. The rekey rows therefore log in first
  with RFC 4252's `none` method, as an empty-password account the row's
  `sshd` admits.
- **OpenSSH's client offers `zlib@openssh.com` even with `Compression=no`.**
  Its KEXINIT is otherwise byte-identical to burrow's after the cookie, when
  it is given burrow's lists.

## den over burrow, measured (B4)

den at `ac2332b` (`burrow-den.toml`), built by its own tools at its own
toolchain pin, and its pinned git 2.56.0 as the server. Each den row runs
through burrow-as-`ssh` and through the pinned `ssh` against one `sshd`
(`AcceptEnv GIT_PROTOCOL`), and every compared field is equal: den's exit
code, stdout and stderr, the local and server repositories, and the
`GIT_PROTOCOL` each service received (`version=2` for upload-pack and
receive-pack alike; nothing for the v0 wrapper). The black-box findings:

- **The pinned `ssh` reads `~/.ssh` from the passwd entry, never `$HOME`;**
  burrow reads `$HOME` (for PAX, which has no passwd database).
  den passes neither `-F` nor `UserKnownHostsFile`, so the rows install
  their `.ssh` as the container user's own, and both clients read the same
  files.
- den's argv is the one bw02 measured, for every URL form: `-p` only for
  `ssh://host:port`, the user kept in the destination,
  `GIT_PROTOCOL=version=2` sent by `SendEnv` for both services. Its remote
  words are git's: the program bare when it is plain (letters, digits and
  `._/+-`), quoted when it is not, the path always quoted, so `sshd` is
  sent `git-upload-pack 'PATH'` (the `den-command-*` rows; den quoted the
  program too until den#65).
- A remote's own stderr (`error: denying non-fast-forward …` from the
  server's receive-pack) reaches den's stderr through either client byte for
  byte.
- den's clone holds the whole history in memory: through the pinned `ssh`,
  its peak RSS was 348 MiB at 30 commits, 954 MiB at 60, 3.3 GiB at 120 and
  12 GiB (the container's cap, SIGKILLed with 40 more large files) at 300
  (den#63). `tools/measure-den`'s fixture is sized to that.

**GitHub, read only** (`tools/check-github`): its server offers
`curve25519-sha256` (burrow's choice; the pinned `ssh` chooses
`mlkem768x25519-sha256`), strict kex, an `ssh-ed25519` host key whose
fingerprint is the published `SHA256:+DiY3wvvV6TuJJhbpZisF/zLDA0zPMSvHdkr4UvCOqU`,
`chacha20-poly1305@openssh.com`, and EXT_INFO naming `server-sig-algs` and
`publickey-hostbound@openssh.com`. With no identity, both clients are
refused with `git@github.com: Permission denied (publickey).` and exit 255.
GitHub's ssh service does not hand a command to a shell: it parses it, and
takes the program as a bare word, as git sends it (`git-receive-pack
'PATH'`). A quoted program word (`'git-receive-pack' 'PATH'`), which a
shell accepts, is refused (`Invalid command: …`) through either client.
den sent that form until den#65, which sends a plain program word bare;
burrow passes the command as `ssh` does and changed nothing for it.
`tools/diag-command-form` puts the old form, git's, and den's own argv at
the pin to the live fixture, read only: the old form is refused, and den's
argv is accepted through both clients.

## burrowd, measured (B5)

`tools/measure-server`, release burrowd against the pinned `sshd` and the
one-process build of burrowd (a row program), through the pinned `ssh`, one
host key and one account, interleaved: five rounds of 20 logins each
(connect to the first byte of `echo`), three of 64 MiB through `cat`, the
minimum of each; the server's CPU is the listener's reaped descendants'.
Two takes on the Linux x86-64 desktop's six-CPU block, each with nothing
beside it: a development take at `f61a9ae` and the final gauntlet record at
`be9684f`, with no change between them to the code a login or a transfer
runs:

| measure | development take: burrowd, `sshd`, ratio | final record: burrowd, `sshd`, ratio | margin |
|---|---|---|---|
| connect to the first byte, wall | 80.1 ms, 109.6 ms, 0.73x | 83.5 ms, 111.5 ms, 0.75x | 6x |
| server CPU per login | 6.0 ms, 10.5 ms, 0.57x | 6.5 ms, 11.5 ms, 0.57x | 25x |
| 64 MiB through `cat`, wall | 1.31 s, 0.83 s, 1.58x | 2.01 s, 0.39 s, 5.20x | 12x |
| 64 MiB through `cat`, server CPU | 1.22 s, 0.47 s, 2.60x | 1.89 s, 0.22 s, 8.59x | 50x |

The login ratios agree between the takes. The transfer's do not: between
them `sshd`'s own transfer went from 0.83 s to 0.39 s and burrowd's from
1.31 s to 2.01 s, so on this machine the transfer ratio is not stable to
better than about three times, and one take says little about it. The
margins still hold across that spread: the worse take, 5.20x and 8.59x, is
under half of each, and each margin is at least twice the top of the range
the prediction gave (6x for the wall time, 20x for the CPU).

The one-process build took 79.6 ms and 90.3 ms to the first byte and 5.0 ms
and 5.5 ms of CPU a login, so the separate processes cost 1.01x and 0.93x in
wall time (no difference these takes can see) and 1.20x and 1.18x in CPU
(two more forks a connection, and the monitor's pipe round trips). `sshd`
re-executes itself for every connection, which burrowd, a fork of its
listener, does not; the transfer's cost is burrowd's ChaCha20 and Poly1305
in checked `int` code.

## PAX

`tools/build --static` makes `target/static/burrow` and
`target/static/burrow-keygen`: x86-64 ELF executables with no interpreter
and no dynamic section (`tools/check-static`), which run on a Linux userland
other than the one that built them. A PAX install puts them at `/bin/ssh` and
`/bin/burrow-keygen`. What PAX must supply, and the workarounds:

| need | state |
|---|---|
| a resolver | none on PAX (wolf-lang#831, wolf-std#4): `~/.ssh/config`'s `Host github.com` with `HostName` an address from `api.github.com/meta`'s `git` ranges and `HostKeyAlias github.com`, so den keeps `git@github.com:…` and the known_hosts line is GitHub's published one |
| entropy | burrow reads `/dev/urandom`, refused by name (`entropy_unavailable`) where absent |
| the network | the console kernel's network is a PAX gap of its own |
| `$HOME` | `~/.ssh` is read from `$HOME`: PAX needs no passwd database |
| GitHub's host key | `/etc/ssh/ssh_known_hosts` is read by default, after `~/.ssh`'s files, so a published line pinned there needs no `~/.ssh/config` |
| a root store | not needed: ssh has no X.509 |

## Gaps, named

- wolf-std has no peer address (wolf-std#140): on linux burrowd reads the
  client's address from `/proc/net/tcp` and `tcp6`; elsewhere the log line
  and `SSH_CLIENT` say `UNKNOWN` and port 0.
- wolf-std cannot hand an accepted connection across `exec`, so every
  burrowd process is a fork of the listener, never a fresh image.
- On macOS burrowd serves only the user who runs it (wolf-std cannot change
  a process's user there), and refuses to start as root.
- burrowd runs commands only: no shell, pty, subsystem, X11, agent or
  forwarding, each refused by name.
- burrowd checks crypt(5)'s `$7$` alone (wolf-std's scrypt): a stock Linux
  account's `$y$` (yescrypt) or `$6$` password is refused by name where
  `sshd` checks it. burrowd changes no password (no
  SSH_MSG_USERAUTH_PASSWD_CHANGEREQ): an expired one is changed at the
  console. wolf strings cannot be wiped, so a password stays in the worker's
  and the monitor's memory until each exits.

- wolf-std has no SHA-1 (wolf-std#131): `src/sha1` is burrow's own, for
  hashed known_hosts names only, until it lands.
- wolf-std has no entropy source; burrow reads `/dev/urandom` (PAX needs one).
- The pinned wolf-std's Ed25519 `verify` accepts small-order keys
  (cofactorless, as RFC 8032 allows); `verify_strict` lands in a later std.
  Its `sign` is not constant time (above).
- wolf-std has no one wait over a socket and a file at the pin: the session
  waits up to 5 ms on each in turn when idle (`src/session`).
- No pty (so no interactive shell at a terminal; `-T` runs the shell
  without one), agent, forwarding, certificates, or RSA and ECDSA keys;
  each is refused by name.
- No resolver on PAX (wolf-lang#831, wolf-std#4): `HostName` and
  `HostKeyAlias` let den's `git@github.com:…` reach an address under
  GitHub's own host key (above).
- den's ssh rows run in the local gauntlet only: den's git oracle is built
  in den's own image, whose digest a CI runner is not held to reproduce.
